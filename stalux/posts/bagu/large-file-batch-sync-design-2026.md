# 大文件批量同步系统：性能、幂等与断点恢复设计

> 适用场景：对象存储或远端文件导入 MySQL 等关系型数据库。重点不是单纯提高写入速度，而是在性能、数据库压力与失败恢复之间取得稳定平衡。

很多同步任务最初都很直接：读一行、写一行、更新一次进度，再继续下一行。数据量小时它足够简单；文件变大后，事务提交、网络往返、重复 I/O 和重试一致性都会迅速成为问题。

本文围绕七个问题展开：文件如何读取和缓存、数据库如何批量写入、幂等记录如何参与事务、如何控制资源压力、断点如何恢复，以及为什么单个任务通常应保持串行。

## 1. 文件读取：从重复 I/O 到单次流式处理

### 1.1 重复读取的成本不只是“读了两遍”

一种常见实现是先下载文件，再扫描一次做格式校验和摘要计算，最后扫描第二次执行导入：

```text
远端存储
→ 下载到本地文件
→ 第一次扫描：格式校验和摘要计算
→ 第二次扫描：数据库写入
```

它带来的成本包括：

- 完整的本地磁盘写入；
- 两次文件扫描和解析；
- 容器临时盘空间与磁盘带宽竞争；
- 对操作系统 page cache 的占用；
- 多个任务同时运行时的缓存淘汰和 I/O 抖动。

第二次扫描可能命中 page cache，不一定再次触发物理磁盘读取；但大文件仍会挤占其他进程的缓存，因此不能把它当作“没有成本”。

### 1.2 单次执行尝试中的流式读取

更合适的方式是：**在一次执行尝试中**，远端文件只成功读取一遍，同时完成解析、校验、摘要计算和原始内容缓存：

```text
远端 Reader
    ├─ 格式校验
    ├─ 摘要计算
    └─ 原始内容缓存
```

完整扫描结束后，系统拥有：

- 文件是否合法；
- 数据规模与汇总摘要；
- 一个可重新扫描的本地数据源。

之后的导入只读取本地缓存，不再访问远端存储。需要区分的是：进程崩溃后的恢复仍会重新读取并校验源文件；“单次读取”描述的是一次运行尝试，不是整个任务生命周期只读一次。

### 1.3 内存与临时文件的混合缓存

把全部内容放进内存速度最快，但不适合无限增长的文件。可设置固定内存阈值：

```text
小文件 → 保存在原始字节数组中
大文件 → 自动回退到临时文件
```

回退应保持连续：

1. 开始时将字节写入内存；
2. 超过阈值后创建临时文件；
3. 将已读取的内存内容写入该文件；
4. 后续字节继续写入同一文件；
5. 不重新打开当前远端 Reader。

内存中应优先保存原始字节，而不是同时保留所有结构化记录。结构体切片、索引 map 和大量指针会明显放大内存与 GC 压力。临时文件也要在成功、失败和取消路径上清理，并纳入磁盘使用量监控。

## 2. 数据库写入：从单行事务到批量短事务

### 2.1 单行事务为什么慢

若每行都单独提交，十万行就可能产生十万次事务：

```text
BEGIN
写入幂等凭证
更新业务统计
更新同步进度
COMMIT
```

瓶颈通常不在 SQL 的计算本身，而在网络往返、提交时的 redo log 和 binlog、复制、高频更新同一进度记录，以及连接反复进入事务状态。

### 2.2 批量短事务

正确的批量化不是“整个文件包进一个大事务”，而是将固定数量的记录组成中等大小的批次：

```text
读取 N 行
→ 按目标表分组
→ 使用多值 INSERT / UPSERT
→ 汇总更新进度
→ 提交事务
```

一个批次通常包括：批量写入幂等凭证、批量更新业务数据、更新一次进度、提交事务。这样能把数百行数据压缩成少量 SQL 往返。

以下是单纯的批量写入示例：

```sql
INSERT INTO import_records (task_id, row_no, record_key)
VALUES (1001, 1, 'a'), (1001, 2, 'b'), (1001, 3, 'c');
```

批次不是越大越好。过大的批次会延长锁持有时间，扩大回滚代价和 binlog 峰值，也会让连接被占用更久。应根据单批耗时、连接池占用、复制延迟与数据库负载调整，而不是固定一个“万能数值”。

### 2.3 累加式 UPSERT 不是天然幂等

MySQL 的 UPSERT 适合合并同一业务键的数据，例如：

```sql
-- MySQL 8.0.19 及以上可用的新行别名写法
INSERT INTO daily_stats (account_id, stat_date, total)
VALUES (101, '2026-10-26', 5),
       (102, '2026-10-26', 8) AS incoming
ON DUPLICATE KEY UPDATE total = daily_stats.total + incoming.total;
```

它在唯一键冲突时会继续累加，因此**重复执行同一批数据会重复计数**。旧项目可能仍在使用 `VALUES(total)`，但该形式已在 MySQL 8.0.20 起弃用；新版本应优先使用行别名。[MySQL 官方文档](https://dev.mysql.com/doc/refman/8.4/en/insert-on-duplicate.html)

若业务要求“重试不重复累加”，应先由幂等表原子确定本批首次生效的记录，再只按这些记录计算业务增量。不能将 `INSERT IGNORE` 后的全部原始数据直接拿去累加，也不能仅根据一条 UPSERT 的总影响行数推断每一行是否首次写入。

实际实现中，常见做法是使用事务内的批次暂存表或批次标识，保存并返回本批被接纳的记录集合；后续业务 SQL 只 join 这个集合。具体方案可以不同，但“幂等判定结果”和“业务增量来源”必须一一对应。

## 3. 原子边界：凭证、业务结果和进度必须一起提交

一个批次至少涉及三种状态：

```text
幂等凭证
业务结果
同步进度
```

它们必须处于同一个事务中：

```text
凭证、业务结果、进度
要么全部提交
要么全部回滚
```

如果业务结果已经提交而进度未更新，恢复时会再次处理该批；如果进度先推进而业务结果失败，恢复时又会错误跳过数据。同步进度不是展示字段，而是恢复算法的一部分。

此外，这个结论有两个前提：所有相关表均使用支持事务的存储引擎，并且事务内不执行不可回滚的外部副作用，例如调用外部接口、发送不可撤销消息或执行 DDL。

一个批次的结构可以是：

```sql
START TRANSACTION;

-- 1. 在事务内确定本批真正首次生效的记录集合 new_rows。
--    其实现可基于暂存表、批次标识和 (task_id, row_no) 唯一约束。

-- 2. 仅基于 new_rows 更新业务统计。
UPDATE account_stats
SET total = total + 2
WHERE account_id = 101;

-- 3. 仅当当前 checkpoint 仍为批前位置时推进进度。
UPDATE import_tasks
SET checkpoint_row = 502
WHERE id = 1001 AND checkpoint_row = 500;

COMMIT;
```

代码必须检查每条语句的错误与影响行数。若幂等判定、进度条件或业务写入出现异常，应回滚整批并重新核对状态，而不是带着不确定结果继续提交。

### 3.1 同一任务必须有唯一写入者

`WHERE checkpoint_row = 500` 是一道并发保护，但不能替代任务互斥。多个恢复实例若同时处理同一任务，可能同时构造同一批数据，增加死锁、重复工作和错误处理复杂度。

因此应在任务开始时取得租约、分布式锁，或在数据库中锁定任务行；租约还需要可续期，并在进程退出后能够超时释放。单个任务在任意时刻只允许一个写入者，checkpoint 才能可靠地表示“已完成的连续前缀”。

## 4. 资源治理：主动限速与连接池保护

离线导入不能只追求跑满数据库。写入过快可能耗尽连接池、抬高 CPU 与 I/O、增大 redo/binlog 压力和复制延迟，并影响在线请求。

### 4.1 提交后的限速

可在每批提交并完成必要后置处理后，等待一小段时间：

```text
提交数据库事务
→ 完成必要后置处理
→ 等待一小段时间
→ 执行下一批
```

两百个批次、每批等待一百毫秒，大约增加二十秒任务时间。这是用可预期的离线耗时换取在线稳定性。更进一步可依据连接池等待、数据库 CPU、复制延迟和错误率做自适应限速。

等待不能放在事务中：事务内等待会无意义地占用连接、锁和 undo 记录。Go 中应在提交成功后再做可取消的等待；高频循环可使用 `rate.Limiter` 或复用 `Timer`，避免为每个批次创建 `time.After` 定时器。

```go
if err := tx.Commit(); err != nil {
    // 提交结果可能不确定，先读取 checkpoint 再决定后续动作。
    return err
}

select {
case <-time.After(100 * time.Millisecond):
case <-ctx.Done():
    return ctx.Err()
}
```

离线脚本最好使用独立或更保守的连接池配置；优化重点是提升单连接有效吞吐，而不是盲目增加连接数。

## 5. 断点恢复：将进度定义为连续前缀

### 5.1 为什么不从头逐行判重

恢复时重新扫描整个文件、为每一行查询一次数据库虽然直观，但会产生大量额外读取，也会让幂等表承担恢复主流程。

更合适的定义是：

```text
checkpoint = 当前文件中已经完整提交的连续前缀
```

恢复流程则变为：

1. 读取任务状态并取得该任务的写入租约；
2. 重新读取、解析并校验原文件；
3. 校验 checkpoint 对应的文件前缀；
4. 跳过已提交前缀，从下一条记录重新组批；
5. 每次提交后继续推进 checkpoint。

恢复的主要成本是顺序扫描文件，而不是大量数据库逐行查询。

### 5.2 checkpoint 必须绑定稳定输入

仅记录行数还不够。若源文件被替换，即使总行数相同，每一行也可能已经不同。任务元数据至少应固定对象版本 ID（优先）、完整文件哈希、总记录数，以及必要时的解析规则版本。ETag 只有在确认对象存储语义可代表内容版本时，才能作为辅助校验。

“行号”也应定义清楚：是物理文件行、过滤空行后的数据序号，还是解析后的业务记录序号。恢复与首次导入必须使用完全相同的定义。还可以校验已跳过前缀的汇总值，确认 checkpoint 确实对应当前文件。

### 5.3 事务中断与提交结果不确定

在所有写入均处于同一 InnoDB 事务的前提下，进程在批次中途崩溃，稳定状态只有两种：

- 当前批未提交，事务回滚，进度停在批前；
- 当前批已提交，业务结果与进度一起前进。

若网络在 `COMMIT` 时断开，客户端无法仅凭报错判断提交是否成功。此时不能立即重试，而应在重新取得任务租约后查询 checkpoint：

```sql
SELECT checkpoint_row
FROM import_tasks
WHERE id = 1001;
```

- 等于批前进度：可以重新处理该批；
- 等于批后进度：说明该批已提交；
- 两者都不等于：停止任务并告警，先核对状态。

这个判断成立的前提同样是：同一任务没有其他写入者，且 checkpoint 的推进严格遵循连续前缀。

## 6. 并发模型：为什么同一任务优先串行

假设两个批次同时执行：

```text
批次 A：文件前半段
批次 B：文件后半段
```

如果 B 先提交、A 后失败，单个“已处理行数”已经无法描述状态：已提交的数据不再是连续前缀，恢复也不能直接跳过前 N 条。

所以在只维护一个 checkpoint 时，同一个任务应按文件顺序串行处理。并发 goroutine 未必提高整体吞吐，因为数据库写入、日志、复制、连接池和存储 I/O 都是共享瓶颈；它还可能放大锁冲突与峰值压力。

未来若必须并行，应重设同步协议，而不是只增加线程：例如为每个分片维护独立 checkpoint，给每个批次独立状态，或维护可合并的完成区间。只有在最终能重新合并成连续前缀时，恢复逻辑才仍然清晰。

## 7. 整体链路与观测指标

完整处理链路可以概括为：

```text
取得任务租约
→ 远端文件单次流式读取
→ 格式校验、摘要计算与缓存
→ 按顺序读取缓存并组批
→ 在批量短事务内完成幂等判定、业务写入和进度推进
→ 提交后执行后置处理与限速
→ 最终校验摘要、累计进度并清理缓存
```

线上至少应记录：文件版本和摘要、每批记录数与耗时、当前 checkpoint、重试次数、死锁/锁等待超时、数据库连接池等待、复制延迟、临时文件体积和最终校验结果。这样在任务变慢或恢复失败时，才能判断瓶颈究竟来自读取、解析、数据库、限速还是资源竞争。

## 结语

大文件同步系统的核心并不是“更快地写 SQL”，而是同时解决四件事：减少无效 I/O 和数据库往返；控制对共享基础设施的压力；让每个已提交批次的状态清晰一致；并在任意中断后安全恢复。

单次执行中的流式读取、批量短事务、事务内的幂等判定、提交后限速、连续前缀 checkpoint，以及单任务唯一写入者，共同构成了一套相对简单且可靠的方案。它适用于对象存储文件导入、历史数据迁移、统计回灌与对账导入等多数离线同步场景。
